# 供應商評核系統 — 完整架構與重構分析報告

> 產生日期：2026-07-29
> 目的：重構前的全面體檢，供「大改前後端 + 擴充功能」規劃使用。
> 分析範圍：後端 `server/`、前端 `src/`、Excel/業務邏輯、設定/部署/資料模型。

---

## 0. 總體結論（TL;DR）

這是一個**功能可運作、但工程品質偏低**的系統，典型「無程式底子的人長出來的」樣貌：能跑、但幾乎沒有分層、沒有測試、沒有版控、大量複製貼上、設定與文件全面脫節。

核心問題可濃縮成 **6 條主軸**（依重要性）：

1. **業務計算邏輯被複製了 4 份**（前端 service / 前端元件 / 前端匯出 / 後端），而且**跟文件公式不一致** → 最高風險，任何評分改動都可能算錯。
2. **兩個巨型單檔**：後端 `index.js` 5912 行、前端 `ReportContext.tsx` 806 行（外加 `VendorManagement` 993、`YearlyReport` 871）。
3. **安全性薄弱**：前端授權不可信、token 存 localStorage、後端權限檢查 3 種寫法混用、預設弱密鑰、docker-compose 明文密碼進版控。
4. **資料一致性風險**：後端完全沒有 DB 交易、迴圈內單筆 upsert（N+1）。
5. **設定與部署混亂**：4 套並存的埠號、schema 孤兒檔、migration 無 baseline、文件全部對不上實際 code。
6. **零測試、零 CI、零版控**：改壞無法回復、無回歸保護。

> 建議：重構**不是「小修」而是「有計畫的分層重寫」**。但要先建立安全網（Git + 測試 + 計算邏輯集中），再動刀。

## 2. 🔴 最高優先：業務計算邏輯的四重複製（跨前後端）

這是整個系統**最危險**的地方，也是重構第一件該做的事。

同一套評分規則目前散落在**至少四處**，靠人工保持同步：

| 計算 | 位置 |
|------|------|
| SQM LAR 評分階梯 (30/28/26/22/18/14) | `services/reportService.ts:15`、`components/QualityReport.tsx:24`、`utils/excelExport.ts:5`、`server/src/index.js:15` |
| CAR 公式 `40 - 10×客訴 - 5×arr - 3×未準時` | `reportService.ts:10`、`server/src/index.js:10` |
| 等級門檻 (95/85/75/60) | 後端 `index.js` 至少 5 處 + 前端 `reportService.ts:91` + `ReportContext.tsx:337` |
| 年度分數 (月均×0.9 + 稽核×0.1) | `YearlyReport.tsx:311`、`ReportContext.tsx:337`、`server/src/index.js`(4 處) |
| numberUtils (roundTo3Decimals 等) | `src/utils/numberUtils.ts` ≡ `server/src/utils/numberUtils.js`（逐字重複） |

**而且文件已與程式碼漂移**（`docs/計算規則與判定邏輯說明.md` 寫品質基數 `90 - 2×ARR...`，實際 code 是 `40 - 10×客訴...`；降級交期門檻文件寫 16、code 是 15）。**目前文件不可信，需以 code 為準重新校對。**

→ **重構方向**：抽出單一 `shared/scoring` 純函式模組（含所有門檻常數），前後端共用；文件重新對齊 code；補上對拍測試。

## 3. 後端問題（server/src/index.js, 5912 行）

### 嚴重
- **維護模式永遠失效**：`if (maintenanceMode)`(L5840) 在模組載入時求值，但該旗標要到 `startServer()`(L5898) 才設定 → 整段降級路由形同虛設。
- **弱預設密鑰/密碼**：`JWT_SECRET` 預設 `'dev-secret'`(L91)、維護帳號 `admin/admin123`、seed admin 固定密碼。env 缺漏即上線 → token 可偽造。
- **錯誤細節外洩**：多處把 `e.message` 直接回前端（L291/545/4366/5563…）。
- **輸入驗證缺失**：僅 login/改密/建使用者用 zod，其餘寫入端點直讀 `req.body`，`Number(year)` 未防 NaN。

### 高
- **完全沒有 DB 交易**：季/月 PUT 在迴圈裡 upsert 後再 deleteMany、多個刪除端點連續刪 → 中途失敗留髒資料。
- **N+1**：季/月 PUT、batch 匯入都在 `for` 迴圈內逐筆查詢+寫入。
- **記憶體無界成長**：`chatHistory`(L1031) 與 `cache`(L1025) 都是無上限 Map。
- **到貨明細**：整份 Excel 轉 base64 塞進 JSON 回傳(L5538)、同步阻塞事件迴圈。

### 中
- **巨型 handler**：`queryDatabase`(L1313, ~1350 行)、`/api/ai/chat`(L3294, ~630 行)、兩支 `yearly-evaluation`(各 ~270 行)、`arrival/process`(~420 行)。
- **權限檢查 3 種寫法混用**：`requireAdmin` / `roleAllowed()` / 手寫 `if role !==`。
- **大量重複**：SQM 與 OSAT 兩套幾乎對稱的 CRUD、兩支近乎相同的年度評鑑彙整。

**建議分層**：`app.js` + `config/env`（fail-fast）+ `middleware/{auth,error,validate}` + `routes/` + `controllers/` + `services/{scoring,yearlyEvaluation,ai,arrival,vendor}`。

## 4. 前端問題（src/）

### 核心架構層
- **ReportContext 是「神級 Context」**：806 行、44 個介面成員、混雜 5 種職責（setter / 業務計算 / 資料抓取 / 髒狀態追蹤 / 年度計算引擎）；還直接把內部 `setState` 暴露到介面、用 `window` 事件 + `setTimeout` 觸發重算，破壞單向資料流。
- **無資料快取層**：手刻 `periodStore` / `loadMonthlyVersionRef` 重新發明 react-query 的快取/去重/取消。
- **token/role 存 localStorage**：易受 XSS；且前端 `RequireRole` 用可被竄改的 role 授權 → **前端授權不可信，後端必須再驗**。
- **無 ErrorBoundary**：計算或 render 例外會白屏。
- **死碼**：`suzhouReportService.ts` 無任何引用，卻維持一套獨立評分公式。

### 頁面/元件層
- **巨型元件**：`VendorManagement`(993, 35+ useState, 5 個對話框全塞一個 return)、`YearlyReport`(871, 一個 170 行 useEffect)、`AIChatBot`(558)、`RobotAdmin`(528, 四套平行 state)。
- **報表三兄弟高度重複**：`QualityReport`/`PurchaseReport`/`ComprehensiveReport` 的表格骨架、規則 Accordion、物料篩選邏輯逐字重複 → 可抽一套 data-driven `<ReportTable>` 框架。
- **死 props / 殘留耦合**：`VendorManagementPage:22`、`SQMVQMHomePage:147` 傳了對方不接受的 prop；`Navigation` 與 `YearSelectionDialog` 的年份載入邏輯整段重複。

**建議**：拆 ReportContext → 多個小 context/hook + 導入 TanStack Query；抽 `<ReportTable>` 框架；計算全移 `reportService`；大元件拆子元件 + hooks。

## 5. Excel / 工具層問題

- **suzhou 與 gangshan parser 幾乎整檔複製**（`suzhouExcelParser.ts:116` ≡ `gangshanReportExcelParser.ts:113`），欄位靠**硬編碼索引 `row[2]…row[21]` + 行內註解**維護。
- **exporter 的 sheet 定義 + 欄寬陣列**在 osat/suzhou 間逐欄複製。
- 已有通用 `dataExport.ts` 泛型匯出，但**沒人用**，各 exporter 各自組 workbook。
- **建議**：抽宣告式「欄位對應 schema + 通用解析/匯出引擎」，讓各廠區只差一份 schema。

---

## 6. 設定 / 部署 / 資料模型問題

- **4 套並存的埠號**：實際 3006(容器)/12009(對外)，但 start.sh 說 3001、**所有文件說 12017**、PS 腳本清的又是別組 → 沒一份對得上。
- **機密進版控**：`docker-compose.yml` 明文寫 DB root 密碼、JWT_SECRET、OLLAMA_API_KEY（註解自己說不該留，卻留了）→ 應輪替並移出。
- **兩個系統共用一個 DB**：va_ 評核表（12）+ 半導體表（cp_data_review 等 4 張，屬別的程式，只為避免 `db push` 誤刪而塞進 schema）→ 應剝離。
- **schema_new.prisma 是孤兒檔**且比正式檔還舊（命名誤導），應刪。
- **migration 不完整**：無 baseline 建表、無 `migration_lock.toml`、首個 migration 表名沒 va_ 前綴；實際靠 `db push` + 執行期 `ensureVendorColumns()` 補欄位。
- **build 不做型別檢查**：`build:check`(含 tsc) 存在卻沒人用，Docker/文件都用 `build`；strict 形同虛設。
- **除錯殘留檔**：`server/check_cols.sql`、`check_table.sql`、`_check_users.js`（後者 L37 語法還是壞的）。
- **無 CI/CD、無 .github/**。

## 7. 建議的重構路線圖（分階段，先建安全網再動刀）

### 階段 0：安全網（動任何 code 前）
1. `git init` + 首次提交（目前完全無版控，最高風險）。
2. 輪替已洩漏機密（DB 密碼、JWT_SECRET、Ollama key），移出 docker-compose。
3. 為核心計算補**對拍測試**（純函式最好測），作為重構的回歸保護。

### 階段 1：計算邏輯集中（最高價值、風險可控）
4. 抽 `shared/scoring` 單一計算模組（含常數），前後端共用；刪除四處複製。
5. 重新校對並修正 `docs/計算規則與判定邏輯說明.md`（以 code 為準）。

### 階段 2：後端分層
6. 拆 `index.js` → routes/controllers/services；統一 auth 與錯誤處理；補 zod 驗證中介層。
7. 多步驟寫入加 `$transaction`，迴圈 upsert 改批次；修維護模式 bug、fail-fast 檢查 env。

### 階段 3：前端重整
8. 拆 ReportContext + 導入 TanStack Query；計算移入 service。
9. 抽 `<ReportTable>` 框架與共用 hooks；拆巨型元件；加 ErrorBoundary。

### 階段 4：設定/部署/資料模型收斂
10. 統一埠號、統一 build:check、加 CI；剝離半導體表；補 migration baseline；刪孤兒檔與除錯殘留。
