# 供應商評核系統 — 重構計畫書

> 產生日期：2026-07-29　｜　搭配閱讀：[重構分析報告.md](重構分析報告.md)
> 狀態：**草案，待業主決策**。本計畫尚未動任何 production code。
> 前提：單人／小團隊開發、內部系統、現有功能需盡量不中斷。

---

## 0. 指導原則

1. **先安全網、再動刀**：沒有 Git 與測試之前不做大改。改壞要能一鍵回復、要有回歸保護。
2. **每階段都能跑**：採漸進式，任一階段結束系統都是可運作、可部署的狀態；不做「拆到一半跑不起來」的大爆炸重寫。
3. **計算邏輯單一真相來源**：所有評分規則集中一處，前後端共用，並用測試鎖住。
4. **先收斂、再擴充**：先把重複與風險清掉，讓程式好加功能，再做新功能——避免在爛地基上疊新東西。
5. **不過度工程**：這是內部工具，選穩定主流方案（TanStack Query、zod、Vitest），不追時髦、不引入微服務等重量級架構。

## 1. 目標架構

### 1.1 後端目標結構（取代 5912 行單檔）

```
server/src/
  app.js                  # 建 express app、掛 middleware、註冊 routes
  server.js               # 啟動、DB 連線、維護模式判斷（修好現有 bug）
  config/
    env.js                # 集中讀取+驗證環境變數，缺關鍵值 fail-fast
  db/
    prisma.js             # PrismaClient 單例
  middleware/
    auth.js               # auth() / requireRole()（統一成一種寫法）
    validate.js           # zod 驗證中介層
    errorHandler.js       # 統一錯誤處理，不再各自外洩 e.message
  routes/                 # 只做路由對應 → controller
    auth / users / sqmvqm / osat / ai / vendors / arrival / maintenance
  controllers/            # 解析 req/res，呼叫 service
  services/
    scoringService.js     # ← 與前端共用的計算（見 1.3）
    yearlyEvaluation.js   # 合併目前兩支近乎相同的年度彙整
    aiService.js          # parseQuestion / queryDatabase / Ollama
    arrivalService.js     # 到貨明細 Excel 解析 + supplier mapping
    vendorService.js
  utils/                  # logger / numberUtils（改引用 shared）
```

### 1.2 前端目標結構

```
src/
  api/                    # 型別化 API 層（取代 any 散落）
    client.ts             # axios 實例（統一 login 也走這）
    sqmvqm.ts / osat.ts / vendors.ts / ai.ts ...
    dto.ts                # 後端 wire 格式的型別（DTO）
  hooks/

  state/

    sqmvqm/ osat/ vendors/ admin/ ai/
  components/
    report/ReportTable.tsx  # data-driven 報表框架（三兄弟合一）
    common/                 # DecimalField、RulesAccordion、AsyncTable、ErrorBoundary...
  lib/
    scoring.ts            # ← 與後端共用的計算（見 1.3）
    excel/                # 宣告式欄位 schema + 通用 parse/export 引擎
```

### 1.3 共用計算模組（front + back 單一真相）

```
shared/ (或 packages/scoring)
  scoring.ts / scoring.js    # calcLARScore / CAR / gradeFromScore /
                             # getAuditComponent / annualScore / 降級判定
  constants.ts               # 所有門檻與係數（95/85/75/60、權重、扣分表）
  scoring.test.ts            # 對拍測試：鎖住每條公式
```
- 前端 `src/lib/scoring.ts` 與後端 `server/src/services/scoringService.js` 都 import 同一份；
- 若共用 build 太麻煩，退而求其次：一份原始碼 + 同步腳本 + 對拍測試，確保兩邊不漂移。

## 2. 分階段計畫

> 每階段標註：**目標 / 工作項 / 產出 / 驗收標準 / 風險 / 粗估**（粗估為單人時間，僅供相對參考）。

### 階段 0 — 安全網（動 code 前的地基）　粗估：0.5–1 天
- **目標**：讓任何後續改動可回復、可驗證；堵住已知外洩機密。
- **工作項**：
  1. `git init` + `.gitignore` 複查（確認 `.env*`、`.env.tunnel`、`node_modules` 都忽略）+ 首次提交現況。
  2. 建 remote（Gitea/GitHub 私有）並推送。
  3. 輪替已洩漏機密：DB 密碼、`JWT_SECRET`、`OLLAMA_API_KEY`（docker-compose 目前明文），改用 `.env` 注入。
  4. 導入測試框架（後端 Vitest/Jest、前端 Vitest + React Testing Library），跑一個 smoke test 確認 pipeline 通。
- **產出**：有版控的 repo、乾淨的機密管理、可跑的測試指令。
- **驗收**：`git log` 有初始提交；`npm test` 前後端都能跑；docker-compose 不含明文機密。
- **風險**：低。機密輪替需協調實際 DB/服務，需業主配合。

### 階段 1 — 計算邏輯集中（最高價值、風險可控）　粗估：2–3 天
- **目標**：消除四重複製的評分邏輯，建立單一真相 + 測試鎖定。
- **工作項**：
  1. 盤點現有四處計算，**以 code 現況為準**萃取出正確公式（不信文件）。
  2. 建 `shared/scoring`（LAR/CAR/等級/年度分數/稽核類型/降級判定）+ constants。
  3. 寫**對拍測試**：用現有真實資料（69 供應商/138 季報）跑舊 vs 新，確保數值完全一致（這是安全重構的關鍵）。
  4. 前端 `reportService`、`QualityReport`、`excelExport`、後端 `index.js` 全部改引用 shared；刪 `suzhouReportService` 死碼（或併入）。
  5. 校正 `docs/計算規則與判定邏輯說明.md` 與 code 一致。
- **產出**：一份計算模組 + 測試；四處重複歸零；文件可信。
- **驗收**：對拍測試全綠（新舊輸出逐筆相同）；grep 不到重複公式。
- **風險**：中。公式萃取要小心；靠對拍測試把關可控。

### 階段 2 — 後端分層　粗估：4–6 天
- **目標**：把 5912 行單檔拆成可維護分層，修安全與一致性風險。
- **工作項**：
  1. 抽 `config/env`（fail-fast）、`db/prisma`、`middleware/{auth,validate,errorHandler}`。
  2. 按領域拆 routes/controllers/services；SQM 與 OSAT 對稱 CRUD 參數化共用；合併兩支 yearly-evaluation。
  3. **權限檢查統一成一種寫法**（`requireRole`）。
  4. 多步驟寫入加 `prisma.$transaction`；迴圈 upsert 改批次；**修維護模式失效 bug**。
  5. 全端點補 zod 驗證；統一錯誤處理不外洩 `e.message`。
  6. `chatHistory`/`cache` 換有上限的 LRU；到貨明細改串流/暫存檔而非 base64 塞 JSON（可延後）。
  7. 補 controller/service 單元測試。
- **產出**：分層後端、交易保護、統一驗證與錯誤處理。
- **驗收**：所有既有 API 行為不變（用測試或手動回歸清單驗證）；維護模式真的會啟用。
- **風險**：中高。路由多，需逐一回歸；建議一個領域一個領域搬、每搬完就測。

### 階段 3 — 前端重整　粗估：5–8 天
- **目標**：拆神級 Context、消元件重複、導入資料快取。
- **工作項**：
  1. 導入 TanStack Query，把 `loadMonthly/loadAnnual/yearlyEvaluation` 等改為 query hooks；移除手刻 `periodStore`/`versionRef`。
  2. 拆 `ReportContext`：伺服器資料交給 Query，context 只留「編輯中暫存 + 髒狀態」；移除 `window` 事件 + `setTimeout` 重算，改衍生狀態。
  3. 抽 `<ReportTable>` data-driven 框架，Quality/Purchase/Comprehensive/SQMVQMPage 收斂為欄位設定。
  4. 拆巨型元件：VendorManagement→表格/表單對話框/批量/清空 + `useVendors`；AIChatBot→`useChat`+子元件；RobotAdmin→四分頁各自元件。
  5. 加 `ErrorBoundary`；統一 API 錯誤解析 util；`login`/`useFileUpload` 改走共用 axios。
  6. 型別收斂：`type Grade`、`UserRole` 入 types、DTO 型別、消 `any`。
  7. 補關鍵元件/hook 測試。
- **產出**：模組化前端、資料快取、可重用報表框架。
- **驗收**：各頁功能與現況一致；無白屏；主要流程有測試。
- **風險**：中高。UI 迴歸面大，建議依 feature 分批、每批人工過一次。

### 階段 4 — 設定/部署/資料模型收斂　粗估：2–3 天
- **目標**：清掉設定混亂與孤兒，建立 CI。
- **工作項**：
  1. **統一埠號**（挑一個對外埠，程式/Docker/vite/start 腳本/文件全對齊）。
  2. build 統一用 `build:check`（tsc 生效）；加 CI（lint + type-check + test + docker build）。
  3. 刪 `schema_new.prisma` 孤兒、`check_*.sql`、壞掉的 `_check_users.js`。
  4. 補 Prisma migration baseline + `migration_lock.toml`，停用 `db push`+執行期補欄位。
  5. **剝離半導體 4 張表**（獨立 schema/client 或至少 README 標注非本系統擁有）。
  6. 更新／合併部署文件，對齊實際。
- **產出**：一致的設定、CI 保護、乾淨 schema。
- **驗收**：CI 綠；乾淨 DB 能用 migration 建出完整 schema；文件與實際相符。
- **風險**：中。migration baseline 需對現有 DB 小心操作。

### 階段 5 — 功能擴充（地基整理好之後）　粗估：視需求
- 前置：階段 1–3 完成後，新增報表/評核維度/OSAT 啟用/AI 強化/權限稽核通知等都會容易許多。
- 具體項目待業主看過網站後再細談（本計畫先保留接入點，見第 6 節）。

## 3. 相依關係與建議順序

```
階段0(安全網) ─┬─► 階段1(計算集中) ─┬─► 階段2(後端分層) ─┐
               │                    └─► 階段3(前端重整) ─┼─► 階段4(設定收斂) ─► 階段5(擴充)
               └────────────────────────────────────────┘
```
- 階段 0 必須最先。
- 階段 1 應緊接在後（它讓 2、3 都受益，且風險最低、價值最高）。
- 階段 2 與 3 可並行或擇一先行（前端重整可先靠現有 API；後端分層不影響前端行為）。
- 階段 4 可隨時穿插（尤其「統一埠號 + CI」可以很早做）。

## 4. 測試策略

| 層級 | 工具 | 重點 |
|------|------|------|
| 計算（純函式） | Vitest | 對拍測試鎖公式；最高投報，優先做 |
| 後端 API | Vitest + supertest | 每個領域搬遷後跑回歸 |
| 前端元件/hook | Vitest + RTL | 報表框架、關鍵表單、query hook |
| 端到端（可選） | Playwright | 登入→上傳→計算→儲存→匯出 主流程 |

原則：**先為「要重構的部分」補測試，再重構**（characterization test），確保行為不變。

## 5. 技術選型待決清單（之後要你點頭）

- 資料抓取：**TanStack Query**（建議）vs 維持手刻。
- 驗證：後端 **zod**（已有依賴）擴大使用。
- 測試：**Vitest**（與 Vite 同生態，建議）。
- 共用計算：monorepo `shared/` 直接 import vs 單檔同步。
- 半導體表處理：獨立 schema vs 只標注。
- 對外埠號：沿用 12009 vs 改回文件的 12017 vs 其他。
- Node/DB：MySQL 5.7 已 EOL，是否列入升級（可延後）。

## 6. 擴充功能的接入點（重構如何為擴充鋪路）

- **新報表/評核維度** → 有了 `<ReportTable>` 框架 + shared scoring，新增一種報表 = 一份欄位設定 + 一組公式常數。
- **OSAT 模組啟用** → 後端分層後，OSAT 與 SQM 共用參數化 CRUD/評鑑，啟用只差資料與 UI 接線。
- **AI 問答強化** → `aiService` 拆出後，換模型／改 prompt／加查詢類型都局部可控。
- **權限/稽核/通知** → 後端統一 `requireRole` + errorHandler 後，加操作稽核 log、Email 通知（已有 `email_recipient` 表）成本低。
